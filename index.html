주소 검색 성능 개선

Overview

OCR로 읽은 비표준 주소를 표준 주소에 연결하는 검색을, 실무에서 쓰던 LCS 전수 탐색과 Elasticsearch n-gram 역색인으로 비교했습니다. 개인정보 없는 합성 데이터로 100건부터 1천만 건까지 같은 조건을 재현해 정확도와 지연시간을 측정했습니다.

Intro

같은 질의, 두 가지 검색 경로

합성 데이터 생성

표준 주소에 OCR 오류 규칙을 적용해 질의를 만듭니다. 같은 seed로 100건·1만 건·1천만 건을 생성하고 정답 ID로 채점합니다.

LCS 전수 탐색

실무에서 쓰던 방식의 재구성입니다. 후보마다 최장 공통 부분열을 계산하므로 데이터가 늘어난 만큼 느려집니다.

Elasticsearch n-gram

질의를 2~4-gram으로 분해해 역색인에서 겹치는 문서만 후보로 모읍니다. 「테헤란노」처럼 오타가 든 gram은 색인에 없어 버려지지만 나머지 gram이 정답을 가리키므로, 오타 한 글자에 검색이 통째로 실패하지 않습니다. 전체 후보 비교도 사라집니다.

Contribution

재현 가능한 벤치마크 설계

  • 개인정보 없는 합성 주소 생성기 — seed 20260917, 주소 ID별 고유 지번을 보장해 서로 다른 정답이 같은 문자열을 갖는 충돌 제거
  • 100건부터 1천만 건까지 다섯 시나리오를 같은 CLI(generate → index → compare)로 실행 — Java 21 · Gradle · picocli · Jackson, Elasticsearch 클라이언트 없이 java.net.http로 직접 호출
  • Top-1·Top-5·MRR, p50·p95·p99, QPS를 정답 ID 기준으로 측정하고 원본 JSON을 그대로 보관

두 검색 경로 구현·비교

  • LCS 전수 탐색 — 모든 후보와 LCS를 계산하는 Java 기준선. 적재 시 alias를 한 번만 정규화하고 두 행 int[] DP와 Top-5 힙으로 구현
  • Elasticsearch 2~4-gram 역색인 — Docker Compose 단일 노드(8.17.4 · 2GB heap)에 1천만 문서를 370초에 색인, 약 1.8GB
  • n-gram을 고른 이유 — 단어 단위 역색인은 오타가 든 토큰이 색인에 없어 검색 자체가 실패하고, 코사인 유사도는 오타 하나로 벡터가 움직여 순위가 흔들림. 2~4-gram은 오타를 gram 몇 개의 손실로 가두고 minimum_should_match 55%로 그 손실을 허용

Deep Dive

작을 때는 단순하게,
커지면 역색인으로.

같은 seed와 오류 규칙으로 만든 주소를 두 방식에 넣었습니다. 정확도를 정답 ID로, 속도를 p50·p95와 QPS로 확인한 결과, 1만 건 근처에서 교차됐습니다.

제약
  • LCS는 모든 주소 후보와 문자열을 비교해 비용이 데이터 규모에 선형 비례
  • 1천만 건에서는 한 질의가 약 7초 — 온라인 요청으로 처리 불가
  • 실제 고객 주소는 쓸 수 없어 합성 데이터로 같은 조건을 재현
판단
  • 100건에서는 LCS가 33배 빠름 — 검색 엔진은 HTTP 왕복과 고정 비용만으로 2~3ms
  • 1만 건에서 교차(ES 1.35배) — 10만·100만·1천만 건에서 9배·37배·196배로 벌어짐
  • 후보가 늘면 두 방식 모두 Top-1이 떨어지는데 LCS가 더 크게 떨어짐 — 1천만 건에서 79% vs 86%
선택
  • 1만 건 이하 매핑 테이블은 LCS로 단순하게 유지
  • 대규모는 n-gram 역색인으로 후보를 찾고 상위 후보만 LCS로 재순위 — 오타에 강한 후보 회수와 정밀한 순위 결정을 나눠 맡김
  • LCS 기준선도 Elasticsearch와 같은 JVM 위에서 실행해 언어 차이가 결론에 섞이지 않게 함

시연 — 검색어 하나, 두 검색 경로

격자의 점은 매핑 테이블을 줄여 그린 것이고, 실제 후보 수는 고른 규모 그대로입니다. OCR 오류가 섞인 같은 검색어를 넣으면, LCS는 점을 전부 열어 보고 Elasticsearch는 검색어를 n-gram으로 쪼갠 뒤 역색인에 걸리는 점만 엽니다. 시간 표기는 모두 실측값입니다.

    Trouble Shooting

    n-gram을 사용한 오타 보정

    Trouble
    • 전수 탐색을 대신할 후보 축소 방식이 필요했는데, OCR 질의는 「서울특벌시 강남구 테헤란노 152」처럼 오탈자를 몇 개씩 품고 들어옴
    • 단어 단위 역색인은 「테헤란노」가 「테헤란로」와 다른 토큰이라 색인에 걸리지 않음 — 정답 문서가 후보에서 아예 빠짐
    • 코사인 유사도는 문자열 하나를 벡터 하나로 만들기 때문에 오타 한 글자가 벡터 전체를 움직여 순위가 크게 흔들림
    Cause
    • 두 방식 모두 비교 단위가 「토큰 전체」 또는 「벡터 하나」라, 오타가 그 단위 전체를 오염시킴
    • OCR 오류는 한 글자 치환·삭제, 공백 제거, 행정구역 축약처럼 국소적인데 비교 단위는 국소적이지 않았음
    • 후보를 놓치면 뒤의 재순위가 아무리 정밀해도 복구할 수 없음 — 회수 단계가 오타에 강해야 함
    Solution
    • 2~4-gram 역색인 — 문자열을 두세 글자 단위로 잘라 색인하므로 오타는 gram 몇 개의 손실로 그치고, 나머지 gram이 정답 문서를 가리킴
    • 색인 전 문자·숫자만 남기는 char_filter로 공백·기호 차이를 제거하고, minimum_should_match 55%로 오탈자 gram 손실을 허용
    • 1천만 건 1,000질의에서 Top-5 97.7% · p50 37.79ms — 오타가 섞인 질의로도 후보를 놓치지 않으면서 전체 비교를 없앰. 남은 Top-1 격차는 후보 안에서 LCS 재순위로 좁히는 것이 다음 단계

    Retrospect

    후보 찾기와 순위 정하기는 다른 문제

    1만 건에서 98.9%였던 Elasticsearch Top-1이 1천만 건에서는 90.7%로 내려갔지만, Top-5는 97.7%를 지켰습니다. 정답을 후보에 올리는 일은 역색인이 해냈고, 그 안에서 1위를 고르는 일이 규모와 함께 어려워졌습니다.

    배운 점

    검색을 한 방법으로 끝내려 하지 않고, 놓치지 않는 회수 단계와 정밀한 재순위 단계로 나눠서 봐야 한다는 것을 숫자로 확인했습니다.

    100건에서는 LCS가 33배 빨랐다

    검색 엔진은 HTTP 왕복과 고정 비용만으로 2~3ms를 쓰기 때문에, 후보가 적을 때는 전수 탐색이 오히려 빨랐습니다. 역색인이 앞서기 시작한 것은 1만 건 근처부터였습니다.

    배운 점

    더 빠른 방법은 데이터 규모를 정해야 답할 수 있는 질문이었습니다. 교차점을 직접 재 두니, 작은 매핑 테이블은 단순하게 두고 큰 테이블에만 역색인을 쓰는 기준을 숫자로 설명할 수 있었습니다.
